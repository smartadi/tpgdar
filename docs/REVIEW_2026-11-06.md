## 3. Method questions for Aditya (not bugs; no change without approval)

- **M1: ridge chosen with a test fold.** Script 12 `pick_ridge` fits on folds 2 to 4 and validates on fold 1; fold 1 is later
  a test fold. Only the edge-wise rows use that ridge; the GDAR and symmetric TP rows (the headline) don't.
- **M2: the rank-3 triangle is not the smallest enclosing triangle.** `_enclosing_triangle` puts all three sides on hull
  edges. The true minimum-area triangle needs only one side flush with the hull (O'Rourke et al. 1986). On a near-square hull
  (0,0), (1,0), (1.2,1), (0,0.9) it returns a corner at (0, -5), area 3.5 against a hull area of about 1.0. Farther
  vertices mean a larger polytope for the LMI and vertex systems that are extrapolations. Affects scripts 12c, 13, 15,
  16 and 18 (through 13).
- **M3: `fit_windowed` doesn't do what its docstring says.** The docstring says it concatenates each bin's windows; the code
  fits each window and averages the coefficients, which shrinks short windows toward the ridge prior. No script uses it.
- **M4: soft sum-to-one in `tp._barycentric`.** The constraint has a fixed weight of 1e3 and is renormalised afterwards.
  Exact for points inside the hull; for points outside, the reported `outside` distance depends on the scale of the
  coordinates. Diagnostic only.
- **M5: h-step VAF across unlabelled samples.** `h_step_vaf` propagates with the hold operator (index 0) wherever a target
  label is -1 inside the horizon. Those samples aren't scored, but they feed the later steps.

## 4. Is the structure "proper OOP"? Does it need restructuring?

**The library's style is fine.** `gdar_tp` is a functional core with dataclass containers: `fit_*` functions that take
data or sufficient statistics and return a small model object (`GDARModel`, `QLPVModel`, `TPModel`, `Polytope`, `TPGDAR`,
`SymTP`, `LDS`, `SynthesisResult`). That is the usual shape for scientific Python (scipy, statsmodels) and suits this
project: folds share Gram matrices, so fitting from statistics beats an sklearn-style `fit(X)` on every object. An
abstract-base-class hierarchy would add code without fixing anything below.

**What does need restructuring is around the library, not its style:**

1. **Scripts are used as a library.** `scripts/12_tp_vs_gdar_ios.py` is imported by 11 other scripts through
   `importlib.import_module("12_tp_vs_gdar_ios")`, and `15_nine_node_control.py` by 3. They hold the real-data pipeline
   (loading, labels, folds, evoked kernels, per-trial statistics, Sigma, held-out likelihood, K and ridge selection). Until
   today none of it had a test.
2. **Duplicated helpers.** Companion matrix three times (`control.companion_form`, script 12 `rho`, script 15 `comp`);
   statistics twice (`tpgdar.trial_stats`/`stack_stats`, script 12 `trial_cond_stats`); `sigma_of` (11, 12); `knn_support`
   (09, 10); `gap_rank` (08, 09); `simulate_segment` (02, 04, 05, 06); `interp_coeffs` (02, 06); `certificate`/`lqr`
   (15, 16, 17).
3. **Three operator layouts, no shared interface.** `GDARModel` keeps a list of `A_k` plus `B`; `QLPVModel`, `TPModel`
   and `Polytope` use `(..., N, N, K)` with lags last; `TPGDAR` and `SymTP` use a stacked `Theta (N, K·N [+ inputs])`.
   Conversions are written by hand in scripts (`[th[:, k*N:(k+1)*N] for k in range(K)]`), which is where R1 comes from.
   `TPGDAR` and `SymTP` almost share an interface (`theta_grid`, `theta_at`) but differ on sorting (R2), log
   interpolation and `n_params`.
4. **Private names used as public API.** `sym_tp` imports `tp._barycentric`; scripts import `_quad`, `_solve`,
   `_enclosing_triangle` and `control._solve`.
5. **`io.py` is a stale placeholder** while the IOS Reach and OS-Pulse loaders live in scripts with hard-coded
   `../yazdanlab` paths. `__init__` exports neither `tpgdar`, `sym_tp`, `latent` nor `sim`.
6. Smaller: `control._solve` swallows every solver exception, so a modelling error looks like infeasibility;
   `synthesize_slack_feedback` has no `decay` or `lmi_residual` and returns P in the field named `Q`; `edge_flow` is still a
   Python double loop (open since 10-26); `TPModel.vertex_systems()` returns HOSVD core slices, which aren't convex vertices,
   under the same name as `Polytope.vertex_systems`.

**Proposed restructure (numbers unchanged; needs the gate):**

- *Phase 1, moves only.* `gdar_tp/operators.py`: one `companion`, `spectral_radius`, `theta_to_lags`, `lags_to_theta`.
  `gdar_tp/evaluate.py`: `trial_cond_stats`, `sum_stats`, `pool`, `sigma_of(shrink=)`, `ll_matrix`, `h_step_vaf`,
  `ar_spectrum`, moved verbatim from script 12. `gdar_tp/data/ios_reach.py`: `load`, `labels`, `folds`, `evoked_design`,
  `remove_evoked`, with the data paths in one config object instead of constants. Scripts import from the package; no
  more `importlib` of numbered scripts. Promote `_barycentric`, `_quad`, `_solve`, `_enclosing_triangle` to public names
  (keep the old names as aliases). The tests in `tests/test_script12_helpers.py` move with the code. Check: script 12's
  cached results reproduce to the last digit.
- *Phase 2, interface.* A `typing.Protocol` (not a base class) for operator-grid models: `theta_grid()`, `theta_at(p)`,
  `n_params`, `K`, used by `TPGDAR`, `SymTP`, and thin adapters for `GDARModel` and `QLPVModel`. Fix R1 to R8 and remove
  their xfail markers.
- *Not proposed:* class hierarchies, sklearn-style estimators, or rewriting the fitters.
